# 默认自动交付：规则、入口与限制

这份说明记录本轮把默认完成规则从“人工最终签收”改为“独立自动验收”之后的实际行为。
它描述已经实现并被测试覆盖的部分，以及明确不覆盖的部分。

## 一条默认路径

```text
用户在 DSH 中提出需求
  → delivery_iteration(action=open) 记录需求原文
  → 结构检查 / 覆盖 / 预算：还欠什么、什么过期、还剩多少
  → 实现 → 本地诊断（不是证据）
  → delivery_ci(action=request) 让平台在精确候选上跑冻结验收
  → collector 把这次 attempt 落到 delivery-state
  → 发布前提由晋升 job 用只读令牌在平台上观测
  → 晋升 job 独立认证来源、重算覆盖与预算、原子推进 Baseline
```

不需要用户运行脚本、编辑回执或发表审批评论。需要用户决定的只有实质产品取舍、
新增权限、费用和破坏性操作。

## 完成规则

`completion_policy.mode` 是唯一来源：

| 模式 | 完成条件 | 谁批准 |
|---|---|---|
| `independent_auto`（默认） | 冻结候选上实际执行全部 Required 与累积 Spine；发布前提被平台观测到 | 不需要人工签收 |
| `human_review` | 上述机器条件 + 绑定同一候选/标准/部署的真实人工评审记录 | 用户本人，Agent 无法伪造 |
| 未声明 | 按 `human_review` 处理 | 用户本人 |

未声明按人工处理是刻意的：缺一个字段不能让项目自动变成“可交付”。
`independent_auto` 也不允许留下未迁移的人工评审定义——那会变成暗中的终态门槛。

## 自动验收为什么不是“自称完成”

- 验收 case 在受保护目录里，实现者不能改；CI 结构检查逐文件比对候选与受保护版本。
- 每个 case 必须在这次运行的 `case_results` 里有且仅有一次 `passed`；缺 case、skip、
  失败、绑定过期都会阻塞。
- 自动终态不修改输入对象：原始 Evidence 字节保持不变。
- 发布前提由晋升 job 自己读平台（必需检查是否在该候选上通过、Baseline 引用是否存在、
  验证工作流是否启用）。HTTP 失败、权限不足、未知前提一律 `UNVERIFIED`，不会默认放行。
- 自动模式不生成 owner 回执；人工模式的反伪造约束（同仓库精确评论、真实 User 作者、
  绑定候选/标准/镜像/部署）完全保留。

## 预算规则的一处修正

成功执行仍写入历史并占用总预算，但不再计入同根因失败计数，也不再把无进展窗口推高。
此前三次成功验证会被记成同一个根因失败三次，导致后续正常迭代在晋升时被判为
“需要 Replan”，而事实上并没有反复失败。历史与总预算依然累计，成功不会清零任何东西。

## 限制（必须如实报告）

- 自动结论只覆盖机器可观察结果。交互易用性等主观判断不在其中；需要时由用户主动
  发起人工评审，而不是把它包装成自动通过。
- 候选运行时隔离仍未实现：验证在受保护 CI runner 上执行，隔离后端是欠账，只在
  Baseline 元数据里作为告警记录。
- 本仓库没有独立 staging 通道，验证环境是 `production_like_ci`；这不等于真实 staging。
- `delivery_ci` 只请求并观测工作流。它不持有 Baseline 凭据，`requested` 或 `completed`
  都不等于晋升；派发结果不明确时不会重试，避免重复消耗同一冻结候选。

## 会话内可用的工具

| 工具 | 作用 | 边界 |
|---|---|---|
| `delivery_iteration` | 追加式迭代日志：记录需求、决策、观测到的证据引用、阻塞、结束 | 只是可恢复摘要，不是完成凭证 |
| `delivery_ci` | 按白名单输入派发 `verify` / `promote`，读取精确运行与 job | 无 Baseline 凭据；歧义派发不重试 |
| `delivery_gaps` / `delivery_coverage` / `delivery_resume` / `delivery_attempts` / `delivery_verify_local` | 结构检查、覆盖重算、恢复摘要、预算、本地六门诊断 | 只读；本地一律 `local_diagnostic` |
